# OAuth consent CSRF candidate

This candidate binds each public-client consent page to a short-lived, per-request browser cookie and an HMAC-protected form token. The POST also requires the Origin to equal the gateway's configured public origin (or its derived request origin when PUBLIC_BASE_URL is unset). The cookie is Secure, HttpOnly, host-only, SameSite=Strict and scoped to the root path. An invalid or absent binding is rejected before the pending request or setup code is consumed. Two concurrent authorization pages use different cookie names.

This is a browser CSRF and session-binding control, not authentication of the person at the browser. It does not stop a caller who can open their own consent page and possesses a setup code, nor does it change confidential-client auto-issuance, setup-code minter provenance, grants, existing tokens, or refresh behavior. It does not complete backlog task t_idem_a3fc3a1e.

Compatibility and rollout: only HTTPS clients that retain the host-only cookie and send a same-origin Origin header can complete this interactive flow. A consent page opened before rollout must be restarted; existing OAuth tokens and refresh sessions do not use this POST. Before release, test the actual reverse-proxy/public URL configuration and browser/connector flows with synthetic credentials; ensure PUBLIC_BASE_URL is correct. Independent security review and live verification remain outstanding.

Rollback: revert the commit containing this document and the consent changes; redeploy the previously verified gateway image using the existing release process. No datastore schema or credential change is made. Reverting removes these CSRF protections.

## Local browser verification

An isolated synthetic Fastify backend behind a local HTTPS reverse proxy was tested with Chromium Headless 155.0.8059.12. The proxy forwarded X-Forwarded-Proto and X-Forwarded-Host; the backend used trustProxy and a matching PUBLIC_BASE_URL. Its self-signed certificate was trusted only by this disposable fixture. Chromium actually stored the cookie as Secure, HttpOnly and SameSite=Strict, did not expose it to document.cookie, submitted read-only and synthetic elevated forms, retained the cookie on a wrong-code retry, and removed it on successful submissions. No other browser, live connector or production proxy was tested. Synthetic Fastify tests also cover concurrent tabs, expired and exhausted requests, invalid origins and mismatched cookies and tokens.

The prior `no-referrer` page policy caused Chromium to send `Origin: null` on its same-origin POST; the earlier candidate used `same-origin`. An independent Edge loopback fixture found that `same-origin` sent the full authorization URL in Referer, while `strict-origin` preserved Origin and sent only the origin in Referer. This candidate now uses `strict-origin`; that Edge fixture was HTTP loopback, not the earlier HTTPS proxy or a live connector. Existing retries retain their pending-specific cookie; success and known burned/expired results clear only the corresponding pending cookie. Browser cookie Max-Age remains the expiry backstop when a page is abandoned. Uncertain store errors do not clear the session.
