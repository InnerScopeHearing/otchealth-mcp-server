# OAuth consent CSRF candidate

This candidate binds public-client consent pages to one short-lived browser session cookie and per-pending HMAC-protected form tokens. The POST also requires the Origin to equal the gateway's configured public origin (or its derived request origin when PUBLIC_BASE_URL is unset). The cookie is Secure, HttpOnly, host-only, SameSite=Lax and scoped to the root path. Lax allows a cookie-bearing browser to retain its session across top-level connector navigation; the form POST still requires exact Origin and the pending-specific token. An invalid or absent binding is rejected before the pending request or setup code is consumed. Concurrent pages with the existing session share the cookie but cannot exchange tokens.

This is a browser CSRF and session-binding control, not authentication of the person at the browser. It does not stop a caller who can open their own consent page and possesses a setup code, nor does it change confidential-client auto-issuance, setup-code minter provenance, grants, existing tokens, or refresh behavior. It does not complete backlog task t_idem_a3fc3a1e.

Compatibility and rollout: only HTTPS clients that retain the host-only cookie and send a same-origin Origin header can complete this interactive flow. A consent page opened before rollout must be restarted; existing OAuth tokens and refresh sessions do not use this POST. Before release, test the actual reverse-proxy/public URL configuration and browser/connector flows with synthetic credentials; ensure PUBLIC_BASE_URL is correct. Independent security review and live verification remain outstanding.

Rollback: revert the commit containing this document and the consent changes; redeploy the previously verified gateway image using the existing release process. No datastore schema or credential change is made. Reverting removes these CSRF protections.

## Local browser verification

A synthetic Fastify backend behind a loopback HTTPS reverse proxy was tested with Chromium Headless 155.0.8059.12. The proxy forwarded X-Forwarded-Proto and X-Forwarded-Host; the backend used trustProxy and a matching PUBLIC_BASE_URL. Its self-signed certificate was trusted only by this disposable fixture. Chromium actually stored the cookie as Secure, HttpOnly and SameSite=Strict, did not expose it to document.cookie, submitted read-only and synthetic elevated forms, retained the cookie on a wrong-code retry, and removed it on successful submissions. A separate Edge 156 HTTPS loopback test also passed for that earlier design; no live connector or production proxy was tested. Synthetic Fastify tests also cover concurrent tabs, expired and exhausted requests, invalid origins and mismatched cookies and tokens.

The prior `no-referrer` page policy caused Chromium to send `Origin: null` on its same-origin POST; the earlier candidate used `same-origin`. An independent Edge loopback fixture found that `same-origin` sent the full authorization URL in Referer, while `strict-origin` preserved Origin and sent only the origin in Referer. This candidate now uses `strict-origin`; that Edge fixture was HTTP loopback, not the earlier HTTPS proxy or a live connector. The earlier Chromium check exercised the prior per-request SameSite=Strict design, not this shared SameSite=Lax session; repeat browser and real connector checks before release. The shared cookie is not cleared on success, rejection or expiry of an individual pending request because other tabs may need it. Each consent GET refreshes its 30-minute Max-Age; a pending authorization has its own stored expiry. Cookie eviction or expiry makes an outstanding form fail closed and requires restarting authorization. Two truly simultaneous first GETs without a cookie can generate different session values: the last cookie stored wins, so the other form fails closed and needs restart. No cookie is issued per pending page; repeated abandoned requests use one cookie, but pending records remain bounded by their own existing TTL, not this cookie. Uncertain store errors do not clear the session.

An isolated-data loopback HTTPS-proxy run of the bounded-cookie candidate exercised Chromium Headless 155 with synthetic credentials and store: one Lax/Secure/HttpOnly cookie across repeated pages, read-only and elevated redirect, wrong-code retry, same-origin POST and origin-only Referer passed. This was one tab navigated twice, not independent simultaneous tabs or an external connector. The sandboxed network-namespace run could not launch Chromium due an OS socket denial; the successful local test was not OS-network-isolated. The temporary browser profile was removed. The earlier per-pending design was tested in fixtures and was not deployed by this work. If another deployment issued such cookies, they expire under their existing Max-Age.
