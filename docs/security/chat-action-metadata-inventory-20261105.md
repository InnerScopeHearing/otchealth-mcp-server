# Staged Chat-action metadata inventory

The existing status and result tools require an original job ID; no company queue inventory route was found. This separate candidate adds a CTO-authorized read-only `chat_action_inventory` tool. A request selects exactly one allowlisted company owner lane, a page size of 1–50, and an optional original job ID as an exclusive cursor. The database query restricts type and owner before paging and projects only ID, status, action, owner lane and creation/update timestamps. It never selects request, result, caller hash or other job fields. The handler strictly validates every projected value and fails closed on malformed, unexpected, duplicate or out-of-order records. It does not mutate or execute jobs.

Only the CTO lane is authorized, including against cached or directly invoked handlers. Personal and unknown lanes cannot be selected. This is owner-label filtering, not proof that an incorrectly labeled company record has no protected origin; no job content is inspected to classify it. Legacy malformed records cause a generic error, not silent omission. A running state does not prove a currently active owner, nor does a queued state prove no prior effect. An unknown outcome is not a stored status and cannot be inferred. Original handle and writer/outcome reconciliation requires separate evidence.

Pagination follows ascending opaque IDs without a snapshot. Concurrent inserts, deletes, state changes, inconsistent legacy partitions or duplicate IDs may make an inventory incomplete; repeat or reconcile separately. No count from a partial page represents a fleet total. The candidate is undeployed. Tests use synthetic data and the actual PostgreSQL dispatcher with a mocked driver; no live job or database was accessed. Review role visibility, active backend, indexing, concurrency behavior and rollout before any production use.

## Query bound and ordering follow-on

The repository documents a primary key on `(pk, id)` and contains no events expression-index definition for this cross-partition owner filter and JSON ID sort. That does not establish the indexes actually installed in production; no database catalog or live jobs were inspected. A row limit alone does not bound the scan or sort.

The PostgreSQL-only inventory now uses one checked-out connection and a read-only transaction with `SET LOCAL statement_timeout = '2500ms'` before the fixed projected SELECT. The database, not a JavaScript timer, must abort that statement at the deadline. A failure rolls the transaction back; a failed rollback discards the connection. The shared pool configuration is not changed. This bounds server execution of the SELECT, including lock waits, not necessarily an already-stalled network connection, pool wait, transaction setup or rollback. Mock-driver tests verify statement order, same-client execution and timeout error handling; no real server cancellation was observed. Production timeout, permissions, installed indexes and query plans need independent verification.

The PostgreSQL ID comparison and sort explicitly use the bytewise `C` collation, matching the validated lowercase hexadecimal ID ordering used by the continuation check. The Cosmos fallback adapter concatenates partition ranges without a global merge and can return out-of-order or skipped rows; inventory fails closed for non-PostgreSQL backends rather than claiming its pagination is complete. Pagination remains non-snapshot, and duplicated IDs across inconsistent partitions can still make scans incomplete.
