# OTCHealth MCP Server: Architecture Decision Record (ADR-002)

**Date:** July 8, 2026
**Status:** ACTIVE. Revisit only when one of the triggers in Section 6 fires.
**Owner:** Matt Moore (President, OTCHealth Inc.)
**Author:** OTCHealth CTO agent (Hyperagent/Claude Sonnet 5), per Matt's direct request to formalize this decision
**Audience:** Any engineer or agent (human or AI) touching `src/auth/` or the Descope pilot going forward
**Purpose:** Decide how far the Descope Agentic Identity Hub pilot (shipped additively in PR #90 and PR #91) should go — full replacement of the legacy Azure Key Vault OAuth lane system, permanent parallel operation, or something narrower — and record why, so this isn't re-litigated from scratch every time someone asks "should we finish migrating to Descope?"

---

## 1. Decision

**Neither a full cutover nor indefinite unscoped parallel operation. A staged split by capability:**

1. The legacy Key Vault `oauth-lane-<agent>-id`/`-secret` client_credentials pairs, validated by the self-issued HS256 path in `src/auth/bearer.ts`, remain the **primary, always-available credential path** for every named agent's gateway access. This is the true critical path and keeps zero external dependency in it.
2. Descope (both Access Keys and Inbound App Clients, per PR #90/#91) continues running as a **genuinely additive second path**, opt-in per lane via `DESCOPE_PILOT_LANES`, for the specific capabilities it already provides real value on today:
   - SIEM-grade audit logging (source IP, TLS fingerprint, bot score per action) that the legacy path does not have.
   - The Agentic Identity Console dashboard, for fleet-wide visibility as the agent roster grows.
   - Scriptable ring **membership** changes (who belongs to `ring:exec`, etc.) via Access Key custom claims or Inbound App Client scopes — provably no-deploy-required, unlike the current `FORBIDDEN_AGENTS`/`EXEC_RING` hardcoded arrays.
3. Authorization **rules** (what a ring is actually allowed to do) stay in reviewed TypeScript, gated by `ci.yml`'s green-main check, PR-reviewed, git-tracked. They do **not** move into Descope Policies.
4. Descope Outbound Apps / Connections (the third-party credential vault, distinct from agent-to-gateway auth) is **not adopted** for any production third-party credential yet. It remains a separately-evaluated, later decision — see Section 5.

This is not a rejection of Descope. It is a decision to keep using it exactly where it has already proven real value, without betting the fleet's entire auth critical path on it before the gaps in Section 3 close.

---

## 2. Context

Phase 1 (Access Key provisioning) and Phase 2 (gateway wiring, PR #90 + PR #91) of the Descope pilot were completed and independently re-verified end-to-end on 2026-07-08: all 9 named fleet agents (`clo`, `clo-personal`, `cto`, `cfo`, `coo`, `cro`, `cpo`, `cco`, `developer`) have real, live Descope Inbound App Clients whose tokens the gateway correctly resolves to the right agent identity via `laneFromScope()` / `DESCOPE_SCOPE_LANE_MAP`, with ambiguous scope combinations rejected outright rather than guessed. This is genuinely working, in production, today — additively, alongside the existing Key Vault pairs, which have not been touched or deprecated.

The question this ADR answers is the natural next one: given that it works, should it become the *only* path?

---

## 3. Why not a full cutover (yet)

| Concern | Evidence |
|---|---|
| **Policy authorization rules are Console-UI only** | Confirmed via Descope's own docs and two independent research passes across 48 public Descope GitHub repos: no Policy JSON schema, REST API, SDK method, or Terraform resource exists. Descope's own docs state "cannot be managed with Terraform or via APIs at this time," IaC support "coming soon," no ETA given. Moving authorization rules there would be a regression from the git-tracked, PR-reviewed, `ci.yml`-gated discipline this repo already runs on. |
| **Agentic Identity Hub is young** | ~15 months old as of this research, with only a handful of named production references (Cequence Security, WisdomAI, Daylight Security). A competitor (WorkOS) explicitly calls it "first year of life" — a fair, narrow criticism, not FUD. |
| **Vendor-viability risk** | Descope: founded 2022, ~90-110 employees, $88M total seed funding, no Series A yet as of this research. Small-company risk is real for something now sitting in the auth critical path of every agent action fleet-wide, if it were the *only* path. |
| **Pricing model mismatch with our traffic shape** | Descope bills M2M Exchanges (not MAU) for exactly the kind of traffic our agent fleet generates. Illustrative math (12 agents × 50 calls/day × 30 days ≈ 18,000 exchanges/month) already exceeds the Free tier's 10K from routine operation alone, before any real measurement against actual `otchealth-mcp-server` traffic. The $10K AWS Activate credit is a runway, not a subsidy — no binding quote has been obtained yet. |
| **New single point of failure** | The current self-issued HS256 path has zero external dependency. If Descope becomes the *only* path and its API or JWKS endpoint is unreachable, every agent action fails fleet-wide — a failure mode that does not exist today and would be new, not inherited. |
| **Partial Terraform/IaC coverage** | Inbound Apps and RBAC/FGA schema now have real Terraform coverage (as of provider v0.3.10+, ~2026-04-15 onward). Outbound Apps/Connections and Policies still do not — only an unofficial third-party Terraform provider covers Connections. |

None of these are fatal to Descope as a product. They are reasons not to make it the sole path for a HIPAA-adjacent, revenue-critical fleet's authentication layer while they remain open.

---

## 4. Why not indefinite, unscoped parallel operation either

Running two credential systems forever without a defined split of responsibility is its own risk: more code paths to secure, more surface area for the exact class of bug already found once this session (an ambiguous-scope-resolution edge case, correctly designed to fail closed rather than guess — but it took explicit engineering attention to get right). Parallel operation is justified only because Section 1's capability split gives each system a clear, non-overlapping job: legacy owns the critical path, Descope owns observability/dashboard/membership-scripting. "Keep both because migration is hard" would not be a good enough reason on its own.

---

## 5. Outbound Apps / Connections: explicitly deferred, not rejected

Descope's Outbound Apps feature (a managed vault for *third-party* credentials — Stripe, Shopify, etc. — as distinct from agent-to-gateway auth) was evaluated separately during this pilot. The credential-populate mechanism is now understood and live-verified (`POST /v1/mgmt/outbound/app/user/apikey/upload` for static API keys; `.../oauthtoken/upload` for migrating existing OAuth tokens; a separate user-session browser-consent flow, `/v1/outbound/oauth/connect`, for live OAuth connections — never a direct admin-injected live OAuth token). It has its own open gaps independent of the agent-auth decision above: no official Terraform coverage, a 600 requests/min fetch-side rate limit that would require gateway-side caching at our scale, and OAuth-type connections needing a one-time human consent step. This ADR does not adopt or reject Outbound Apps for production third-party credentials — that is a separate decision, to be made only if a concrete driver emerges (e.g., wanting per-agent-scoped third-party credential access instead of the current one-shared-key-per-Hyperagent-skill pattern).

---

## 6. Triggers to revisit this decision

Any one of the following should trigger an active re-evaluation of Section 1, not a full re-litigation from zero:

1. Descope ships a real Policy Management API and/or Terraform resource for Agentic Policies.
2. A binding, written pricing quote is obtained at OTCHealth's actual or realistically-projected M2M-exchange volume, and it is not alarming.
3. The Agentic Identity Hub shows materially more production maturity (more named references, a full additional year of runtime, ideally a closed Series A for the company).
4. The parallel path has run in production long enough to measure real latency/reliability data, rather than relying on estimates.
5. Outbound Apps gains official Terraform coverage and a concrete third-party-credential-vaulting need arises (see Section 5).

---

## 7. What does NOT change because of this ADR

- PR #90 and PR #91 remain merged and live. No code is being rolled back.
- All 9 named agents keep both credential paths available exactly as they are today.
- `DESCOPE_PILOT_LANES` and `DESCOPE_SCOPE_LANE_MAP` remain live, unchanged.
- No existing Key Vault secret, Access Key, or Inbound App Client is being deleted or rotated as a result of this ADR.

## 8. Acceptance Criteria for This ADR

This document is correctly used when:
- Any future proposal to move authorization *rules* into Descope Policies is checked against Section 3 and Section 6 first.
- Any future proposal for a full cutover away from the legacy Key Vault pairs is checked against Section 6's triggers before proceeding.
- Any future adoption of Outbound Apps for real third-party production credentials treats it as the separate decision described in Section 5, not a rider on this ADR.
- Full supporting evidence (pricing detail, competitive analysis, SDK/API endpoint specifics, reliability history) is kept current in the "Descope Living Document" and the "Descope (OTCHealth)" Hyperagent skill, not duplicated here — this ADR records the *decision and its rationale*, not the full research corpus.
