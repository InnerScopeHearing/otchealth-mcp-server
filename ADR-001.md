**Date:** May 11, 2026
**Status:** LOCKED. Do not revisit during build.
**Owner:** Matt Moore (President, OTCHealth Inc.)
**Audience:** Claude Code agent executing the Perplexity mega-prompt
**Purpose:** Pre-flight the Section 3 architecture choice so Claude Code skips the planning round and goes straight to build.

---

## 1. Decision

Build **Option C (Hybrid)** as specified in Section 3 of the Perplexity mega-prompt.

The Node.js MCP server owns: authentication, tool schemas, input validation, audit logging, all read-path API calls, and simple single-call writes (Track API events and attribute updates).

n8n owns: complex multi-step write orchestration, retries, scheduling, and any future workflow that benefits from visual editing or branching.

This decision is final. Do NOT propose Option A or Option B during build. Do NOT keep both alive conceptually.

---

## 2. Rationale (Five Bullets, Per Spec)

1. **Existing n8n investment.** OTCHealth runs n8n at otchealth.app.n8n.cloud on a Hetzner VPS. Pure Option A wastes that. Pure Option B forces every read call through an unnecessary network hop and turns n8n into a single point of failure for the entire MCP surface.

2. **Read and write asymmetry matches the architecture.** Phase 1 is read-heavy (9 read tools, 4 write tools). Reads need low latency and strict typing, which is the MCP server's strength. Complex writes benefit from retry, scheduling, and human-readable workflow editing, which is n8n's strength.

3. **Audit logging needs one chokepoint.** Section 6.4 requires before and after diffs, correlation IDs, and caller identity on every write. Easiest to enforce at the MCP server boundary, with n8n receiving an already-logged, already-validated payload.

4. **Schema validation belongs at the API edge.** TypeScript plus Zod at the MCP server gives strong typing and rejection of unexpected fields. n8n is dynamically typed by design and forgiving. Validating at the edge before any n8n hop is the correct order of operations.

5. **Failure isolation.** If n8n is down, reads still work. If the MCP server is down, scheduled n8n workflows keep running on their own triggers. Pure A and pure B both create single points of failure.

## 3. Tech Stack (Locked)

| Layer | Choice | Reason |
|-------|--------|--------|
| Runtime | Node.js 20 LTS | Stable, official MCP SDK support |
| Language | TypeScript, strict mode | Static typing, official Anthropic recommendation for MCP |
| MCP SDK | `@modelcontextprotocol/sdk` (official) | First-party, actively maintained |
| Transport | Streamable HTTP, stateless JSON | Easier to scale, official recommendation for remote servers |
| HTTP framework | Fastify | Lighter than Express, better TypeScript support |
| Schema validation | Zod | Official recommendation, ergonomic, inferred types |
| Logging | Pino | Structured JSON, fast, production-grade |
| Container | Docker, multi-stage build | Reproducible deploys |
| Deployment | Railway (Phase 1), Fly.io fallback | Native HTTPS, stable URL, env var secrets, minimal ops |
| HTTPS termination | Railway native | No nginx needed in Phase 1 |
| Secrets | Environment variables only, Railway secrets in prod, dotenv in dev | No secrets in code, logs, or repo |

Do NOT pick Express, SSE-only transport, or stateful sessions. Do NOT use Composio anywhere in the core path.

## 4. Tool Routing (Phase 1)

### 4a. Direct API, in-process (MCP server handles end-to-end)

All read tools, plus simple single-call writes:

- `cio_list_newsletters`
- `cio_get_newsletter`
- `cio_get_newsletter_metrics`
- `cio_get_newsletter_schedule`
- `cio_get_segment`
- `cio_list_segment_people`
- `cio_get_customer`
- `cio_get_template_or_content` (best-effort, return `unsupported_via_api` on failure)
- `cio_get_broadcast_history_for_segment`
- `cio_track_event` (single Track API call)
- `cio_update_customer_attributes` (single Track API call)

### 4b. MCP server then n8n webhook (orchestrated)

Multi-step writes that need retry, diffing, or branching:

- `cio_update_newsletter_variant` (fetch current, diff, write, log, optional notification)
- `cio_duplicate_newsletter` (fetch source, create copy, verify, return new ID)
- Any Phase 2 write tools that require scheduling or retry logic

### 4c. Tool naming convention

Consistent prefix per integration: `cio_` for Customer.io, `shopify_` for Shopify, `intercom_` for Intercom, `n8n_` for n8n meta-tools, `notion_` for Notion. Lowercase, snake_case, action-oriented (`list_`, `get_`, `update_`, `duplicate_`, `track_`).

### 4d. Required MCP tool annotations

Every tool registration must set:
- `readOnlyHint: true` for all `list_`, `get_`, `search_` tools
- `destructiveHint: false` for reads, `true` only for `delete_` or hard-overwrite writes
- `idempotentHint: true` for `update_customer_attributes`, `track_event` with idempotency key
- `openWorldHint: true` for all tools that hit external APIs

### 4e. Output structure

Use `outputSchema` plus `structuredContent` (TypeScript SDK feature) for every tool. Return both text content and structured data. Concise, focused payloads. Paginate where applicable.

### 4f. Error messages

Actionable, not generic. Bad: `"Error: 404"`. Good: `"Newsletter ID 8472 not found. Verify the ID at https://fly.customer.io/env/193366/newsletters or call cio_list_newsletters."` Always include next-step guidance.

## 5. Boundary Contract (MCP server to n8n)

| Field | Value |
|-------|-------|
| Transport | HTTPS POST to n8n webhook URL |
| Auth | HMAC-SHA256 signed payload, shared secret in `N8N_WEBHOOK_SECRET` env var |
| Required headers | `X-Correlation-Id`, `X-Tool-Name`, `X-Caller-Hash` |
| Payload | Validated, sanitized JSON matching the target n8n workflow's expected schema |
| Response contract | `{ success: boolean, result: any, error?: string, audit_payload: { before: any, after: any } }` |
| Default timeout | 30s, configurable per tool |
| Audit log timing | MCP server writes log entry BEFORE n8n call, updates entry on response |

n8n workflows MUST be exported to JSON and committed to the repo under `/n8n-workflows/` for version control. No untracked workflow drift.

## 6. Auth Model

| Hop | Protocol | Secret Source | Rotation |
|-----|----------|---------------|----------|
| Perplexity to MCP server | Bearer token | `PERPLEXITY_CONNECTOR_TOKEN` env var | Manual, quarterly minimum |
| MCP server to Customer.io App API | Bearer | `CIO_APP_API_BEARER` env var | Per Customer.io UI cadence |
| MCP server to Customer.io Track API | HTTP Basic | `CIO_SITE_ID` plus `CIO_TRACK_KEY` env vars | Per Customer.io UI cadence |
| MCP server to n8n webhooks | HMAC-SHA256 signed payload | `N8N_WEBHOOK_SECRET` env var | Manual, quarterly minimum |

Audit log records the SHA256 hash of the inbound bearer token, never the raw value. Token rotation does not break the audit trail because hashes are stable within the rotation window.

### Kill-switch

Implement `POST /admin/revoke` requiring a separate admin token (`ADMIN_REVOKE_TOKEN` env var). Hitting it invalidates the active `PERPLEXITY_CONNECTOR_TOKEN` immediately by writing a new value to a runtime override store. Worth the 30 minutes of work. Cheap insurance against token leak.

## 7. Env Switches (Required by Spec Section 6.3)

| Variable | First-Deploy Default | Purpose |
|----------|---------------------|---------|
| `READ_ONLY_MODE` | `true` | Globally disable all write tools |
| `ENABLE_WRITE_TOOLS` | `false` | Per-environment write enable |
| `ENABLE_HIGH_RISK_TOOLS` | `false` | Gates n8n-routed writes specifically |
| `DRY_RUN_DEFAULT` | `true` | Every write tool defaults to dry-run unless caller overrides |

First production deploy ships with `READ_ONLY_MODE=true`. Write tools light up only after Matt confirms read tools work end-to-end against live Perplexity. Hard gate.

## 8. Phase 4: Evaluations (Required, Not Optional)

Per Anthropic MCP best practices, the build is not complete without 10 evaluation questions.

**Requirements:**
- Independent: each question stands alone
- Read-only: no destructive operations required to answer
- Complex: requires multiple tool calls
- Realistic: a question Matt or his ops team would actually ask
- Verifiable: single clear answer, string-comparison checkable
- Stable: answer does not change minute-to-minute

**Example question shape:**
> "Find all Customer.io newsletters sent in the last 30 days with open rates above 25%, and identify which segment received the highest-performing one."

Output as XML under `/evals/phase1.xml` in the spec's standard format. Claude Code must run the eval set against the deployed server before declaring Phase 1 complete.

## 9. Out of Scope for Phase 1

- Shopify, Intercom, n8n meta-tools, Notion: scaffold only, do NOT implement.
- ElevenLabs, Twilio: not Phase 1, not Phase 2.
- OAuth flow for Perplexity (bearer token is sufficient for v1).
- Multi-tenancy (single Perplexity workspace only).
- Real-time webhook subscriptions from Customer.io (poll-based for v1).
- HTML email rendering or preview generation.

## 10. Compliance Guardrail Module (Spec Section 6.7)

Implement `regulated_data_guardrail` as a middleware layer. If any tool response contains:
- INND ticker mentions in unscheduled marketing contexts
- Patent claim language (OTCHealth and InnerScope own zero patents, never claim otherwise)
- 510(k) clearance claims (Soundwave LLC owns the Sontro 510(k), not OTCHealth)
- A-grade HearAdvisor claims (MatriX is B-grade, never A)
- Pre-shipment availability claims (FDA Establishment Registration not yet filed)
- TReO described as a hearing aid (it is a Personal Sound Amplifier)

...then return the response with a `compliance_warning` field populated and require explicit `acknowledge_warning: true` from the caller before the data is rendered. This protects Matt from Reg FD exposure on a connector that touches investor-adjacent content.

## 11. Open Question (Decision Locked Below the Line)

The Perplexity spec says "bearer token" but does not specify rotation cadence, issuance authority, or leak response.

**Decision:** Single bearer token in env var, manually rotated quarterly, with the kill-switch route from Section 6 above. Good enough for Phase 1. Revisit only if Phase 2 expands to shared connector use across multiple Perplexity workspaces or users.
